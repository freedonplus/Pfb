# 分轮提问脚本（前端）

每轮最多 4 题，使用 AskUserQuestion 工具。选项中推荐项放第一位并标注「（推荐）」。

## 提问纪律（三条，违反即流程错误）

1. **条件题不混排**：同一轮只出"当前一定有效"的问题。互斥条件题（问 App 栈 vs 问 Web 环境）必须拆到**下一轮**按上轮答案动态生成——一次性渲染 4 题的界面上，用户还没选平台就要面对两个互斥问题，必然乱选。
2. **不按项目类型剥夺问询**：不得因为选了「后台管理」就跳过动效、3D、图表、可视化、自研组件的问询。后台项目同样要用 DataTables、ECharts、效率型微交互。剪枝只允许发生在**同一轮内的次级选项**（例如小程序不问构建工具），不允许整域跳过。
3. **不重复已知信息**：对话、工作区代码、历史记忆中已明确的（框架、语言、平台）不再问，直接进回执表并注明"已从上下文确定"。

---

## 第 1 轮 · 平台（必问，只问平台）

本轮目的：确定交付形态。**本轮不放任何条件题。**

1. **目标平台**（单选主平台；如有多端需求在补充里说明）
   - 网站 / Web H5（推荐）：浏览器访问，含 PC 与移动端
   - 微信小程序
   - 移动 App：需要安装包
   - 桌面端：Windows / macOS 安装包

2. **项目性质**
   - 内部系统 / 后台管理
   - 对外产品 / 官网 / C 端
   - 个人项目 / 原型验证

3. **是否已有代码**
   - 全新项目（推荐）
   - 已有代码，需在其上继续（→ 走场景 A 差距检查，方案书以"增量改造"为基线）
   - 已有代码，但准备重写

---

## 第 2 轮 · 平台分支题（按第 1 轮答案动态生成，只出相关的一题）

| 第 1 轮选了 | 本轮问什么 |
| --- | --- |
| 移动 App | **App 技术栈**：uni-app x（推荐，一套代码多端编译原生）/ Flutter（性能极致，Dart）/ React Native / 原生 Kotlin·Swift |
| 网站 / H5 | **目标环境**：PC 为主（后台/工具，推荐）/ 移动 H5 为主（微信内打开）/ PC + 移动自适应 |
| 微信小程序 | **小程序类型**：原生小程序（推荐）/ 需同时出 H5（→ uni-app x 或 Taro） |
| 桌面端 | **桌面方案**：Tauri（体积小，系统 WebView，推荐）/ Electron（内核固定、兼容性稳） |

另有一题与上表并列（作第 2 题）：

2. **是否需要多端一套代码**
   - 不需要（推荐）：聚焦单平台，技术栈最纯粹
   - 需要 2 端以上：优先 uni-app x / Taro，并接受样式与能力折损

## 第 3 轮 · 语言与框架（必问）

1. **开发语言**
   - TypeScript（推荐）：类型安全、可维护
   - JavaScript：小项目 / 快速原型（必须配 ESLint 兜底）

2. **框架**（Web / 跨端场景；App 已由第 2 轮定栈时跳过）
   - Vue 3 + Vite（推荐：国内生态与上手成本最优）
   - React 18+ + Vite（生态最丰富、复杂交互）
   - Svelte / Solid（极致性能，生态较小）
   - 由 App 方案决定（uni-app x / Taro）

3. **构建工具**（小程序可跳过）
   - Vite（推荐）
   - webpack 5（存量 / 需要 Module Federation）
   - Rspack（webpack 兼容 + Rust 提速）

4. **包管理与工作区**
   - pnpm（推荐，含 monorepo 能力）
   - npm / yarn（团队既有习惯）

---

## 第 4 轮 · 业务形态、数据压力与权限（必问）

本轮目的：判断性能等级、表格与图表需求、权限复杂度——**这一轮直接决定阶段 1.5 里"数据表格"与"图表"两组的权重**。

1. **流量模型**
   - 内部系统：员工使用，无公网压力
   - 公网 C 端常规：日 UV 万级以内
   - 公网 C 端高流量：百万级 UV、大促页 → 启用 advanced-checklist

2. **权限模型**（后台与 SaaS 必答，最易返工项）
   - 仅登录态（小项目）
   - RBAC：角色 + 菜单/路由级权限（推荐后台）
   - RBAC + 按钮级/接口级细粒度
   - 多租户 + 数据权限（行级/字段级）
   - 对接已有 SSO / 统一认证（不新建账号体系）

3. **数据规模与表格需求**（决定 DataTables / TanStack Table / AG Grid 选型）
   - 常规分页列表（< 500 行/页），列 < 15
   - 复杂表格：固定列 / 服务端排序筛选 / 列显隐 / 导出 / 行内编辑
   - 大数据量：万行以上、虚拟滚动、树形表
   - Excel 式录入（粘贴、公式、批量校验）

4. **可视化需求**（决定 ECharts / Chart.js / D3 选型）
   - 少量统计图（3–5 个常规图）
   - 运营看板：多图联动、筛选穿透
   - 大屏 / 投屏展示（定时刷新、适配 16:9）
   - 定制可视化（非标准图形、关系图、地图）
   - 无图表需求

---

## 第 5 轮 · UI 与组件策略（必问，不得因"后台"跳过）

1. **UI 组件库**
   - 成熟组件库（推荐后台）：按 `component-libraries.md` 默认推荐矩阵
   - 纯 CSS 框架、不引 JS 组件库：Cirrus UI / Bulma / Pico.css（轻量站、文档站）
   - 原子化 + headless 自建：Tailwind/UnoCSS + shadcn/Radix
   - 自研设计系统：有设计师与组件开发人力

2. **视觉风格**（按项目类型从 `ui-patterns.md` §二 StyleKit 映射给 3–4 个候选；**后台也要给 Dark Mode / Dashboard 风，不要只给企业简洁风**）
   - 说明：主风格只 1 个，辅助元素 ≤ 2 种

3. **动效与交互密度**（无论项目类型都问，只调默认倾向）
   - 克制：仅 hover/过渡，一律纯 CSS
   - 标准：页面转场 + 列表增删 + 加载态（Motion / AutoAnimate 级）
   - 丰富：滚动叙事、时间线编排、数据动画（GSAP ScrollTrigger 级）
   - 3D / WebGL：产品三维展示或 Shader 特效（→ 阶段 1.5 A 组）
   - 注：「要不要动效」与「动效是否合规」分开判断，后者一律过 `ui-patterns.md` §四 红线

4. **主题与图标**
   - 需要暗黑模式 / 主题切换（CSS 变量 token，`light-dark()` 增强）
   - 图标方案：iconify（推荐）/ 自托管 SVG / iconfont / 自定义字体

---

## 第 6 轮 · 渲染方式与数据层（剪枝仅限次级选项）

1. **渲染方式**
   - CSR（推荐：后台、App 内嵌页、工具型）
   - SSR（Nuxt / Next）：SEO + 首屏双需求
   - SSG：官网 / 文档 / 营销页
   - 混合：营销页 SSG + 应用区 CSR

2. **状态管理**
   - 轻量：Pinia（Vue）/ Zustand（React）（推荐）
   - 服务端状态库：TanStack Query / SWR（推荐中大型数据交互）
   - 不需要全局状态（页面级即可）
   - 复杂流程状态机：XState（多步表单、订单流转）

3. **请求层**
   - 统一封装 + 拦截器（推荐）：错误码、401 无感刷新、取消
   - 请求库 + 缓存失效策略（TanStack Query / SWR / vue-request）

4. **国际化**
   - 不需要（推荐）
   - 需要 i18n：语言包懒加载、文案抽离、RTL 评估

---

## 第 7 轮 · 交付约束（必问，决定 mock 策略与方案复杂度上限）

1. **接口就绪度**
   - 接口已就绪，有文档与测试环境
   - 并行开发：后端同时进行 → **必须契约先行 + MSW/mock**
   - 完全没有：先定 mock 数据与字段草案，接口变更走契约评审

2. **设计资源**
   - 有完整设计稿（Figma / 蓝湖等）
   - 只有参考站点 / 风格意向
   - 无设计：套组件库默认 + 少量自定义

3. **存量约束**
   - 全新，无历史包袱
   - 必须沿用既有技术栈 / 组件库（写明版本）
   - 需兼容旧数据、旧路由、旧 URL（影响路由与状态设计）
   - 需兼容旧浏览器 / 旧 WebView（限制现代 CSS 与现代 API 使用范围）

4. **团队与交付**
   - 个人独立开发（方案可精简，文档以"未来自己能看懂"为准）
   - 小团队协作（需约定目录规范、提交规范）
   - 交付甲方 / 他人长期维护（文档与变更记录要求提高，复杂度上限下调）

---

## 第 8 轮 · 工程化与发布（必问）

1. **质量门禁**：ESLint + Prettier + 类型检查（推荐全部启用）/ 仅 ESLint / 暂不需要（需说明理由）
2. **测试范围**：关键业务单测（Vitest，推荐）/ 组件 + E2E（Playwright）/ 不做（不推荐）
3. **CI/CD**：流水线 + 静态托管（推荐）/ 灰度发布 / 手工发布（仅小项目）
4. **监控**：前端监控 + Web Vitals 上报（推荐公网 C 端）/ 仅错误捕获 / 内部工具从简

---

## 阶段 1.5 · 能力池盘点（必做，细则见 `library-catalog.md` §四）

第 8 轮结束后**不得**直接写方案书，先完成能力盘点：

1. **一次性给全貌**：输出 12 行能力域总览（A 3D / B 动画 / C 图表 / D 数据表格 / E 组件库与 CSS / F 图标字体 / G 编辑器 / H 地图 / I 文件媒体 / J 表单交互 / K 状态请求 / L 工程监控），每行给「代表方案 + 本项目默认倾向 + 体积量级 + 一句话价值」。
2. **逐组分轮问**（每轮 2–3 组，≤ 4 题/轮）：选项为「按默认组合（推荐）」「我自选（补充里点名）」「不需要」。正文必须列出该组候选与体积，不能空问"要不要动画库"。
3. **已由前轮确定的组不重复问**：第 4 轮的表格/图表需求、第 5 轮的动效密度已给倾向 → 直接给"据此推导的默认组合"，只让用户确认或改。
4. **平台不适用项直接标注**：小程序无 DOM/WebGL、uni-app x 为 CSS 子集 → 该组标"不适用 + 替代方案"，不给假选项。
5. **输出能力选型回执表**：能力域 / 是否引入 / 选定库 / 加载方式 / 体积预算 / 否决项。
